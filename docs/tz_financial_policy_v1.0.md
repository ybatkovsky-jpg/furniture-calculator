## 1. Цель и границы

Привести расчётное ядро, Telegram-бота, Excel-генератор и КП к единой финансовой модели:

- 30% наценка на расчётную базу `B`;
- отдельная клиентская доставка 10 000 ₽ и отдельная внутренняя себестоимость доставки;
- сохранение наценки `+13%` за безналичную оплату (это не налог);
- налоги и платёжные комиссии — по подтверждённой модели;
- версионирование, снимок параметров и история;
- одинаковый результат в Telegram, Excel, КП и будущей Web-панели.

**Вне границ v1.0:** полноценная Web-панель, CRM, управление производством, оптимизация раскроя. Для них закладываются API/модель данных, но реализация — отдельные этапы.

## 3. Архитектура: единое финансовое ядро

### 3.1. Обязательная схема

```text
Telegram / Excel / KP / Web
        │
        ▼
FinancialService (загрузка политики, снимок, сохранение)
        │
        ▼
FinancialEngine (чистые формулы, без БД)
        │
        ├── CostBaseBuilder → B
        ├── MarkupCalculator → F_base
        ├── TaxPolicy → T, VAT
        ├── PaymentPolicy → P
        ├── DeliveryPolicy → D_client, D_internal, DeliveryResult
        └── FinancialResult → строки, итоги, warnings, status
        │
        ▼
OrderFinancialSnapshot (immutable JSON + нормализованные таблицы)
```

### 3.2. Запреты

- Нельзя дублировать формулы в handlers, Excel или КП.
- Нельзя читать цены напрямую из SQLite в Excel (текущий `template_filler._load_db_prices` — только SQLite; это должно быть удалено).
- Нельзя хранить разные версии одной формулы в интерфейсах.
- Нельзя использовать скрытые коэффициенты вне реестра.
- Нельзя одновременно применять старый `profit_rate` и новый `m`.
- Нельзя убирать или менять `noncash_markup=1.13`: это подтверждённая наценка за безнал, не налог.

### 3.3. Целевые модули

| Модуль | Ответственность |

| `app/domain/financial/models.py` | dataclass-модели `FinancialInput`, `FinancialResult`, `CostBaseLine`, `TaxPolicy`, `PaymentPolicy`, `DeliveryPolicy` |
| `app/domain/financial/engine.py` | чистые формулы, округление, валидация |
| `app/domain/financial/cost_base.py` | сборка `B` из `CostLine` |
| `app/services/financial_service.py` | загрузка политики из БД, снимок, сохранение |

Допускается другая структура, но **один** вход и **один** результат обязательны.

## 4. Расчётная база `B`

### 4.1. Правило

`B` строится из подтверждённых строк затрат:

```text
B = Σ approved_cost_lines
```

В `B` входят:

- материалы и комплектующие;
- производственные операции;
- проектирование;
- монтаж;
- накладные;
- замер;
- прочие утверждённые прямые расходы.

В `B` не входят:

- `D_client`, `D_internal`;
- `T_rev`, `VAT`, `P`;
- наценка `m`;
- скидки/наценки/бонус дизайнера;
- старый `profit_rate`;
- наценка за безнал (`noncash_markup`).

### 4.2. Классификация старых коэффициентов

Текущие `manufacturing_rate=0.80`, `installation_rate=0.55`, `design_rate=0.10`, `overhead_rate=0.05`, `tech_director_rate=0.015`, `measurement_fee=2500` **не являются автоматически утверждёнными затратами**. Для каждого параметра в реестре указывается:

- `value_type`: `percent_of_cost`, `percent_of_revenue`, `fixed_amount`, `coefficient`;
- `calculation_base`;
- `is_cost_base`: входит ли в `B`;
- `status`: `provisional` / `approved` / `archived`;
- `source`.

До утверждения:

- расчёт может быть `provisional`;
- окончательное КП не выпускается;
- в интерфейсе показывается, какие параметры не утверждены.

### 4.3. Запрет двойного учёта

Одна сумма не может быть одновременно:

- в `B` и в `D_internal`;
- в `B` и в `T`/`P`;
- в `B` и в `m`;
- в `B` и в бонусе дизайнера.

`B` не включает `D_internal`; доставка учитывается только в `DeliveryResult`.

## 5. Формулы

### 5.1. Мебель

```text
F_base = B × (1 + m)
```

### 5.2. Налоги/комиссии от выручки

Если `t` и `p` применяются к одной базе `F_net`:

```text
F_net = F_base / (1 − t − p)
```

Для УСН 15% `t = 0`, поэтому gross-up считается только по `p`:

```text
F_net = F_base / (1 − p)
```

Условия:

- `0 ≤ t < 1`, `0 ≤ p < 1`;
- `t + p < 1`;
- иначе `FinancialError` и статус `invalid_policy`.

Если `PaymentPolicy.fee_base = "gross"` (комиссия берётся с суммы с НДС), пересчитать:

```text
p_net = p_gross × (1 + v)
F_net = F_base / (1 − t − p_net)
```

Если у способа оплаты есть фиксированная комиссия `fixed_fee`, которая покрывается ценой:

```text
F_net = (F_base + fixed_fee_net) / (1 − t − p)
```

Если фиксированная комиссия не покрывается ценой — она уменьшает `EBT`. Для `min_fee`/`max_fee` применять `P = max(min_fee, p × base)` с ограничением `max_fee`; при зависимости от цены — итерация до копейки с проверкой сходимости.

Если `fee_base = "net"`, использовать `p` напрямую.

### 5.3. НДС

```text
F_client = F_net × (1 + v)
VAT      = F_client − F_net
```

`VAT` не входит в `B` и не уменьшает `F_net` в P&L; это обязательство. Для ООО «ПРО Мебель» НДС не применяется: `v=0`, `VAT=0`, `F_client=F_net`. При `vat_mode="none"` `v=0`.

### 5.4. Доставка

```text
D_net = D_client / (1 + v)        # если D_client включает НДС
VAT_del = D_client − D_net
DeliveryResult = D_net − D_internal − T_del − P_del
```

Если доставка не облагается НДС: `D_net = D_client`, `VAT_del=0`.

Если `D_client=0`, `D_internal=0`, `T_del=0`, `P_del=0`.

### 5.5. Итог клиенту

```text
OrderTotal = F_client + D_client
```

### 5.6. P&L и УСН 15%

```text
Revenue_net = F_net + D_net
Costs       = B + D_internal
Fees        = P_furniture + P_del
EBT         = Revenue_net − Costs − Fees
Tax_base    = Revenue_net − Deductible_expenses
Tax_15      = 0,15 × max(0, Tax_base)
Min_tax     = 0,01 × Revenue_net
Tax_accrual = max(Tax_15, Min_tax)      # консервативно по заказу
Net_profit  = EBT − Tax_accrual
```

`Deductible_expenses` — подтверждённые для УСН расходы; могут быть меньше `B + D_internal + Fees`. Если все расходы вычитаемые и `P` покрыта ценой, то `Tax_base = 0,30 × B + DeliveryResult`, `Tax_15 = 0,15 × Tax_base`.

`Tax_accrual = max(Tax_15, Min_tax)` — оценка для заказа; по итогам года минимальный налог сравнивается с фактическим налогом за год, поэтому возможен пересчёт резерва. При `EBT ≤ 0` `Tax_15=0`, но `Min_tax` резервируется.

Контроль: `EBT = 0,30 × B + DeliveryResult` (до налога УСН) при покрытой `P` и всех вычитаемых расходах.

### 5.7. Округление

- Все промежуточные расчёты — `Decimal`, не `float`.
- Деньги — до копеек, `ROUND_HALF_UP`.
- Итог клиенту — до рубля, `ROUND_HALF_UP`; способ отображения фиксируется в `FinancialPolicy`.
- Нельзя округлять `B` до рублей до расчёта налогов/комиссий.

## 6. TaxPolicy

### 6.1. Поля

| Поле | Обязательно | Смысл |
|---|---|---|
| `id`, `version` | да | версия |
| `status` | да | `draft` / `provisional` / `approved` / `archived` |
| `tax_regime` | да | для v1.0: `USN_15` (УСН «доходы минус расходы») |
| `tax_base` | да | `revenue_minus_expenses` |
| `profit_tax_rate` | да | `0,15` |
| `min_tax_rate` | да | `0,01` (минимальный налог с доходов) |
| `revenue_tax_rate` | да | `0` для УСН 15% |
| `vat_mode` | да | для v1.0: `none`; НДС не применяется |
| `vat_rate` | при НДС | 0; 10%; 20%; иная подтверждённая |
| `region`, `regional_rate` | да | регион и подтверждённая ставка (15% или пониженная) |
| `deductible_cost_map` | да | какие статьи `B`/`D_internal`/`P` принимаются для УСН |
| `valid_from`, `valid_to` | да | срок |
| `source`, `approved_by`, `approved_at` | да | основание |

### 6.2. Требования

- Налоговый режим не зашивается в код.
- Для УСН 15% `revenue_tax_rate=0`, `profit_tax_rate=0,15`, `min_tax_rate=0,01`; налог не входит в gross-up.
- `Tax_base` считается по подтверждённым вычитаемым расходам, а не автоматически по управленческой `B`.
- Если `tax_regime`/`vat_mode`/`deductible_cost_map` не заполнены, `TaxPolicy.status` не может быть `approved`.
- `t + p < 1` проверяется только для режимов с налогом от выручки; для УСН 15% `t=0`.
- Минимальный налог 1% резервируется по заказу и пересчитывается по итогам года.
- История версий не удаляется.

## 7. PaymentPolicy

### 7.1. Поля

| Поле | Обязательно | Смысл |
|---|---|---|
| `method_code` | да | `cash`, `bank_transfer`, `qr`, `acquiring`, `legal_entity` |
| `name` | да | отображаемое имя |
| `percent_fee` | да (может 0) | процент |
| `fixed_fee` | да (может 0) | фикс. сумма |
| `fee_base` | да | `net` / `gross` |
| `min_fee`, `max_fee` | нет | ограничения |
| `vat_treatment` | да | как учитывать НДС на комиссию |
| `valid_from`, `valid_to` | да | срок |
| `source`, `version`, `status` | да | основание/версия/статус |

### 7.2. Правила

- Наценка `+13%` за безнал сохраняется; она не является налогом/НДС и не заменяет `PaymentPolicy`.
- Комиссия — расход, не «доплата клиента».
- По умолчанию — единая цена для всех способов оплаты; `p` = консервативная оценка (максимум/средневзвешенная) и пересматривается по факту.
- Дифференцированная цена по способу оплаты допускается только отдельным решением директора и после проверки бухгалтером/юристом; в этом случае в КП показывается итоговая цена для выбранного способа, а не «комиссия».
- Если тариф неизвестен — `provisional`; окончательное КП не выпускается.

## 10. Модель данных

### 10.1. Новые сущности

- `FinancialPolicy` — версия политики, статус, автор, даты.
- `FinancialParameter` — реестр.
- `TaxPolicy` — налоговая модель.
- `PaymentPolicy` — способы оплаты.
- `DeliveryPolicy` — правила доставки.
- `OrderFinancialSnapshot` — неизменяемый снимок входа/выхода.
- `OrderActualCosts` — фактические затраты.
- `FinancialChangeLog` — история.
- `PriceListVersion` — версия прайса (или ссылка на `PriceItem.updated_at`/импорт).

### 10.2. Изменения существующих

`Calculation`:

- `financial_policy_id` (nullable для старых);
- `financial_snapshot_id` (nullable);
- `financial_status` (`draft`, `provisional`, `approved`, `legacy_unverified`, `blocked`);
- `payment_method`;
- `parent_calculation_id` (версия);
- `approved_at`, `approved_by`;
- `quote` остаётся для совместимости, но становится ссылкой/дублем снимка.

`CommercialOffer`:

- `financial_snapshot_id` — КП всегда ссылается на снимок.

`Project`:

- без обязательных изменений; при необходимости `default_payment_method`.

### 10.3. Снимок

`OrderFinancialSnapshot` хранит:

- `input`: B-строки, модули, материалы, доставка, способ оплаты, скидки;
- `policy`: версии policy/tax/payment/delivery, значения параметров;
- `result`: B, F_base, F_net, F_client, D, T, P, VAT, EBT, profit_tax, net_profit, margin, markup;
- `warnings`, `status`, `created_at`, `created_by`;
- `engine_version`.

Снимок **не обновляется** при изменении политики/прайса.

## 11. Миграции и старые данные

1. Перед миграцией — backup `data/furniture.db` (`scripts/backup_db.py`) и проверка restore.
2. Добавить таблицы/колонки через Alembic; не через `create_all`.
3. Для существующих расчётов:
   - если `quote` есть — создать снимок `legacy_unverified` с текущими значениями, не пересчитывать;
   - если `quote` нет — `financial_status='legacy_no_quote'`, КП блокируется;
   - не удалять старые поля/расчёты.
4. `alembic upgrade head` — обязательный deploy-step; `create_all` — только тесты.
5. Проверить миграцию на копии БД, затем на production.

## 12. Интерфейсы

### 12.1. Telegram

Менеджер видит:

- `B`;
- `F_base`, `F_net`, `F_client`;
- доставку `D_client`, `D_internal`, результат;
- налоги/комиссии;
- итог клиенту;
- статус (`provisional`/`approved`);
- предупреждения;
- какие параметры отсутствуют.

Менеджер **не может** менять утверждённые коэффициенты. Выбор способа оплаты — из `PaymentPolicy`; если способ не настроен, расчёт `provisional`.

### 12.2. Excel

- Строки — из снимка, не из шаблонных цен.
- Доставка — отдельная строка.
- Налоги/комиссии — отдельные строки.
- Если `provisional` — watermark/лист «ПРЕДВАРИТЕЛЬНЫЙ РАСЧЁТ».
- Запрещено читать SQLite напрямую; цены — из `PriceBook`/снимка.

### 12.3. КП

- Таблица использует снимок.
- Отдельно: мебель, доставка, налоги, комиссии, итог.
- Если `provisional` — КП не выпускается; если `approved` — PDF.
- Шрифты: вся таблица — DejaVu/Arial, не Helvetica для кириллицы.
- Сумма строк должна сходиться с итогом.

### 12.4. Web-панель (позже)

- Директор: утверждение политики, сравнение версий, статусы.
- Бухгалтер: TaxPolicy/PaymentPolicy.
- Технолог: B-параметры.
- Менеджер: только просмотр.

## 13. Тестирование

### 13.1. Unit

1. `B=100000`, `m=0.30`, без налогов/комиссий → `F=130000`, margin=23.08%.
2. `B=100000`, `p=0.02`, УСН 15% (`t=0`) → `F_net=132653.06`, `P=2653.06`, после комиссии 130000.
3. НДС не применяется (`v=0`) → `F_client=F_net=132653.06`, `VAT=0`; НДС не в P&L.
4. Если статус НДС когда-либо изменится: `v=20%` → `F_client=159183.67`, `VAT=26530.61`, `F_net=132653.06`; НДС не в P&L.
5. `p>=1` → ошибка; для режимов с `t>0` также `t+p>=1` → ошибка.
6. Доставка 10000 / internal 6500 → result 3500 до налога/комиссии; без двойного учёта.
7. Доставка не требуется → 0.
8. УСН 15%, все расходы вычитаемые, `EBT=30000`, `Revenue_net=130000` → `Tax_15=4500`, `Min_tax=1300`, `Tax_accrual=4500`, `Net_profit=25500`; 30% — до налога.
9. УСН 15%, `EBT=0`, `Revenue_net=100000` → `Tax_15=0`, `Min_tax=1000`, `Tax_accrual=1000`, `Net_profit=-1000`; убыток/нулевая прибыль не отменяет минимальный налог.
10. УСН 15%, часть расходов не вычитаемая → `Tax_base > EBT`, налог выше 15% от управленческой прибыли.
11. Наценка `+13%` за безнал применяется как `1.13`; это не налог и не НДС.
12. Старый `profit_rate` не применяется; нет двойных 30%.
13. Скидка уменьшает наценку; цена ниже B → `below_cost`, КП blocked.
14. Округление `Decimal`; нет `float`-хвостов.
15. Снимок не меняется после обновления политики.
16. Пересчёт создаёт новую версию.
17. Excel/Telegram/КП дают одинаковый итог.
18. `provisional` блокирует окончательное КП.
19. Роли: менеджер не меняет коэффициенты.
20. Миграция на копии БД.

## 15. Критерии приёмки

- Одинаковые входные данные + версия политики → одинаковый результат.
- 30% — наценка на `B`, не маржа; формула проверена.
- `D_client=10 000` по умолчанию; `D_internal` отдельно; нет двойного учёта.
- `+13%` за безнал сохранён и не подменяется налогом.
- Налоги/комиссии — по утверждённым `TaxPolicy`/`PaymentPolicy`.
- Неполная модель → `provisional`, окончательное КП blocked.
- Все параметры имеют базу/статус/версию.
- Старые расчёты не изменяются; снимки immutable.
- Excel/Telegram/КП используют одно ядро.
- Тесты проходят; миграция проверена на копии.
- 20 заказов пересчитаны; директор/бухгалтер подтвердили.
