## 1. Направление работы

**Продукт.** Telegram-бот + Excel-смета для корпусной мебели. Менеджер загружает альбом
чертежей (PDF → JPEG/скан), система распознаёт мебель и отдаёт смету, которую можно
отдать клиенту и сверить с оператором.

**Главная линия работ (то, ради чего проект):**
чертёж/картинка мебели → VLM разбирает лист по правилам промпта `prompts/unified.txt` →
JSON (`zone_type`, `total_width_mm`, `facades[]`, `drawer_indices[]`, `heights_mm`,
`materials`, `glass`, `notes`, `confidence`) → Python считает **ДСП (панели/раскрой),
кромку, фасады, фурнитуру** → Excel + ответ в чате.

**Метрика готовности — одна:** числа в смете совпадают с операторской сверкой по
эталонному альбому `input_images/Альбом чертежей Рокоссовского-59-79_page-*.jpg`
(12 страниц) и по спорным листам. Эталонные точки истины, заданные пользователем:
- `0008` — детская, кровать **2200 мм, фасадов нет** (дверец не выдумывать);
- `0002` — угловая кухня: разворот **4860 мм**, фасадов **15** (верх 7 + низ 5 + пенал 2 + пенал 1);
- `0001` — прихожая **1650 мм, 2 фасада**; `0004` — гостиная **1830**; `0011` — ванная **1581, 3 фасада**.

**Чего НЕ делаем** (это уже один раз уводило работу не туда):
- OCR счетов/прайсов/текстовых документов — **не целевой кейс**. Задача — чертежи мебели.
- Не «улучшаем промпт вообще», а правим его под конкретные провалившиеся листы.
- Не заводим вторую модель/второй счётчик «на всякий случай» — сначала измерить текущий.

**Приоритеты (сверху вниз):**
1. **Точность** на сложных листах: угловая кухня, многоракурсные листы, стекло, не-кухни.
2. **Повторяемость**: один и тот же лист должен давать одно и то же число (кэш, OCR-заземление, голосование).
3. **Скорость/стоимость**: параллельность, кэш по `(prompt_version, image_sha256)`.
4. **Видимость**: в Excel/чате видно, ЧТО распознали (лист «🧩 Модули (распознано)», строка «🧩 Мебель:»).

## 3. Железные правила (ломать нельзя)

1. **Один расчётный путь ДСП/фурнитуры.** И чат (`calc_engine.calculate_full_cost`), и Excel
   (`template_filler`) обязаны считать количества через `quantity_calc.calculate_quantities`.
   Любой новый счётчик количества = баг, а не фича.
2. **Две схемы модуля — `quantity` в них означает РАЗНОЕ:**
   - распознавание (`image.py`, `recognition_cache.module_to_dict`): `quantity` = число одинаковых
     **корпусов**, фасады отдельно `facades={"count": N}`, ящики `drawers={"count": N}`;
   - ручной ввод (`bot/handlers/manual_input.py`): `filling="doors"|"drawers"|"shelves"|…`,
     `quantity` = число **дверей/ящиков/полок**, ключей `facades`/`drawers` нет.
   Мост один — `calc_engine._dict_to_recognized_module`. Не «исправлять» это в одном месте,
   не проверив второе (иначе ручные расчёты считают 0 фасадов и умножают корпус на число дверей).
3. **Промпт живёт в двух местах** — `prompts/unified.txt` и вшитая константа в `image_analyzer.py`.
   Меняешь правила распознавания — правь оба, иначе прогон в обход файла даст старое поведение.
4. **Секреты только в `.env`** (он в `.gitignore`). Ни ключей, ни токенов в коде/README/AGENTS.md.
   Переменные читаются через `app/config.py` (Pydantic Settings).
5. **Коэффициенты сметы — из `.env`/`config.py`, не хардкодом** (`MANUFACTURING_RATE=0.80`,
   `INSTALLATION_RATE=0.55`, `PROFIT_RATE=0.30`, `NONCASH_MARKUP=1.13` и т.д.). Цены — рубли, `float`.
6. **Не менять основную vision-модель на слабую.** 8B/4B систематически не видят двери/ящики
   (см. §5) — это прямой недосчёт петель и ручек в смете.
7. **Тесты:** `pytest` из корня (в `pytest.ini` `testpaths = tests` — иначе pytest лезет в `temp/`
   и падает на разовых скриптах). Сейчас **410 passed**. Правка расчётов без теста не принимается.
8. **Python 3.12, type hints, async/await, SQLAlchemy 2.0, aiogram 3 FSM.** Не `print()` — `logging`.
   Комментарии, docstring'и, коммиты и сообщения пользователю — **по-русски**.
9. **Ничего не удалять из `input_images/`, `output/`, `temp/`, `pdfs/`** — это артефакты прогонов
   и эталоны (в git они не попадают, восстановить нечем).
10. **Числа не выдумывать.** Если размер не прочитан — писать это в `notes`/«Проблемы», а не
    подставлять правдоподобное значение (главный источник брака в смете).

## 4. Модели, провайдеры, OCR (состояние на 2026-09-07)

`VISION_PROVIDER` в `.env` задаёт **первого** провайдера, остальные остаются резервом
(`image_analyzer._unified_targets`): авто-порядок `local → deepseek → routerai`.
Сейчас локальный сервер на `192.168.1.133:8888` лежит → в `.env` `VISION_PROVIDER=deepseek`,
`DEEPSEEK_VISION_MODEL=deepseek-flash`. Поднимут локал — вернуть `local`.

| Провайдер | Модель | Статус |
|-----------|--------|--------|
| local (unsloth-studio, llama.cpp) | `orcarouter/Qwen3.8-27B-Uncensored-GGUF` — основная; `unsloth/Qwen3-VL-8B-Instruct-GGUF` — запасная | сервер выключен, но именно 27B дала лучший результат (46 дверей на альбоме) |
| deepseek | `deepseek-flash` (DeepSeek-V4.1-Flash, vision) | **рабочий облачный контур**, сейчас первый |
| routerai | Qwen3-VL-235B (ансамбль), GLM-5V (Z.ai) | резерв, фасадные скрипты cloud-only |

**DeepSeek: два обязательных условия, иначе JSON не приходит вообще** (собрано в
`_unified_body`/`_unified_request`):
- `response_format={"type":"json_object"}` — без него весь бюджет уходит в reasoning,
  `finish_reason=length`, `content=""`;
- `max_tokens ≈ 32000` — 16000 не хватает на многоракурсный `0011`.

**Повторы.** 429/5xx — до 2 повторов с backoff 5→15→30 с (учитывает `Retry-After`).
`ConnectError` (мёртвый локальный сервер) и `TimeoutException` **не** повторяются — сразу
следующий провайдер (иначе зависший лист съедал 3×180 с). Таймауты: 900 с local / 180 с облако.

**OCR-заземление размеров.** Числа размерных линий читает **Tesseract 5.4**
(`C:\Program Files\Tesseract-OCR`, `dim_ocr._configure_tesseract_cmd()`), а не VLM.
`select_total_width` выбирает по значению + гейт качества кандидата (`_dim_line_quality`:
центральность 0.50 / ширина строки 0.25 / низ листа 0.15 / повтор числа 0.10): сначала OCR-число
в ±10 % от модели, если оно правдоподобно как цифра размерной линии; иначе — крупнейшее число,
confidence по доминированию над вторым. Проверено на реальном Tesseract-выводе:
`0002 → 4860` (было 9360), `0004 → 1830` (было 3000), `0011 → 1584 ≈ 1581` (было 2581),
остальные страницы оставляют число модели. Заморожено тестом
`tests/test_dim_ocr.py::test_real_album_candidates_calibration`. Страховочная ветка «модель дала
`total_width_mm > 8000` → верим крупному OCR-числу (≥1000 мм)» оставлена в `image_analyzer.py`.

## 5. Проверенное качество моделей (не переспорить заново)

- **`0008` кровать — эталон:** 27B / 4B / 8B / DeepSeek сошлись: детская, 2200 мм, `facades=[]`.
- **`0001` прихожая:** 27B — 1650 / 2 фасада / 1 ящик (детально); 8B — 1650 / 2 двери / 1 ящик
  (эквивалентна для фурнитуры); 4B — 1100 и «дверец нет» (слабая). DeepSeek — 1650 / 2.
- **Батч 12 страниц:** 27B — **46 дверей**, 8B — **15**. 8B систематически не видит двери/ящики/стекло
  (`0003, 0006, 0007, 0009, 0010, 0011` — «дверец нет»), почти не читает высоты, путает зону
  (`0011` → «Постирочная»). Включение thinking не помогает — модель слабее, не параметр.
  **8B как fallback для фурнитуры не годится.**
- **Прогон альбома на DeepSeek:** 11 помещений, 32 модуля, 46 дверей. Совпало: `0001` (1650/2),
  `0004` (1830/2), `0006` (3200/4), `0008` (2200, кровать отсеяна), `0010` (1260), `0011` (1581/3),
  `0012` (800). Расхождения: `0002` — 13 дверей против истины 15 (ширина 4860 верная),
  `0005` — 3080 против 3030 (OCR не дал чисел), `0007` — 1800 во второй попытке против 1600 у 27B.
  Excel прогона: `temp/test_deepseek_run2.xlsx`.
- **`0002` угловая кухня — известная нестабильность:** правило в промпте («не суммируй плечи,
  бери одну линию разворота») добавлено, модель в `notes` пишет правильно («плечо 3030 + 4860 +
  пенал 1530»), но `total_width_mm` всё равно отдаёт суммой — спасает OCR-заземление, не промпт.
- **`confidence` пока не дискриминирует** (high даже на сложных листах) — для авто-флажирования
  не годится, нужна рубрика в промпте или расчёт кодом (OCR↔Vision match).

## 8. Проверка перед словом «готово»

```powershell
.\.venv\Scripts\python.exe -m pytest -q                # ожидаем 410 passed, 0 failed
$env:PYTHONIOENCODING='utf-8'; .\.venv\Scripts\python.exe scripts\check_phases.py  # ожидаем 59/59
```

`PYTHONIOENCODING` обязателен: консоль Windows здесь cp1251, а скрипт печатает рамки/эмодзи —
без переменной падает `UnicodeEncodeError` ещё до проверок (проверено 2026-11-05).

Чек-лист (сначала доказательство, потом отчёт):
1. Прогнать затронутые тесты; если менял расчёт — добавить/поправить тест.
2. Если менял промпт — синхронизировать `prompts/unified.txt` ↔ `image_analyzer.py` и прогнать
   хотя бы один спорный лист (`0002`, `0011`, `0008`) реальным вызовом.
3. Если менял выбор провайдера/`VISION_PROVIDER` — проверить фолбэк (мёртвый local → deepseek).
4. В отчёте пользователю: что изменилось, какие числа до/после, что осталось сломанным.
