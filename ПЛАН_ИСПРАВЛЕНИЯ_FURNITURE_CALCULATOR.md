## 0. Как читать этот документ

1. **ID дефекта = ID задачи.** `P0-01` означает и дефект из аудита, и работу по его устранению. Для групп мелких дефектов введены пакеты `P2-G1…P2-G7`, `P3-G1`.
2. **Статус проверки** в реестре:
   - **З** — подтверждено запуском кода (воспроизведено);
   - **К** — подтверждено чтением кода (участок указан);
   - **И** — подтверждено инструментом (pytest, pip-audit, gitleaks, git);
   - **Г** — гипотеза или не проверено, требуется исследование.
3. **Оценки** даны в рабочих днях одного исполнителя (8 ч) без учёта ожиданий и согласований. Диапазон означает неопределённость, причина указана в карточке.
4. **Этап** — порядок выполнения, а не важность. Внутри этапа задачи можно вести параллельно, если это разрешено карточкой.
5. Все суммы и коэффициенты в примерах — **тестовые или действующие**, а не производственные нормативы. Нормативы подтверждает только собственник (раздел 10).

## 1. Краткое резюме состояния проекта

### 1.1. Вывод

Проект — **продвинутый прототип с рабочей архитектурой распознавания и недоказанным расчётно-ценовым ядром**. Готовность к коммерческой эксплуатации — **2/10**. Использовать как черновик под обязательным контролем технолога можно; как источник цены для коммерческого предложения — нельзя.

Сильные стороны, которые нужно сохранить:

- модульный конвейер распознавания (PDF → рендер → OCR/Vision → модули) с фолбэком провайдеров и кэшем;
- OCR-заземление габаритов (`dim_ocr`, Tesseract) — уже спасало спорные листы `0002`, `0004`, `0011`;
- `quantity_calc.calculate_quantities` как единый счётчик количеств для чата и Excel (покрытие ~96%);
- 343 быстрых unit-теста (2,4 с) и валидатор фаз 59/59;
- разделение слоёв `bot → services → models`.

Переписывать проект с нуля не требуется. Заменить нужно **расчётно-ценовое ядро, слой данных и операторский сценарий**, сохранив распознавание.

### 1.3. Расхождение с постановкой задачи (важно)

В постановке указано «восемнадцать дефектов P1». В итоговом отчёте **23 P1**: 13 финансово-расчётных + 5 безопасности/эксплуатации (P1-12, P1-14, P1-15, P1-16, P1-25) = 18, плюс 5 UI/сценарных (P1-05…P1-08, P1-13). План учитывает **все 23**: игнорировать UI-блокеры нельзя, они не дают довести расчёт до КП. Итого реестр: **8 P0 + 23 P1 + 23 P2 + 5 P3 = 59 дефектов**. Номера `P1-11`, `P1-21`, `P1-22` в аудите отсутствуют; ID сохранены как есть для трассируемости, пропуски не являются потерянными дефектами.

### 1.4. Главный принцип

> **Ни одна сумма не попадает в коммерческое предложение, если система не может объяснить, из каких деталей, материалов, комплектующих, норм и коэффициентов она получена.**

Практическое следствие: у каждой строки сметы должны быть `quantity`, `unit`, `unit_price`, `source_rule`, `price_version`; сумма строк обязана совпадать с `cost_price`; чат, Excel и КП обязаны читать один и тот же `Quote`.

## 4. Архитектура предлагаемого решения

### 4.1. Что сломано архитектурно

Сейчас в проекте фактически **четыре расчётных пути** и **три набора цен**:

| Путь | Вход | Где считается | Куда попадает |
|---|---|---|---|
| 1 | модули из БД | `calc_engine.calculate_full_cost` → `quantity_calc` → `cost_calc` | чат |
| 2 | модули из пайплайна | `template_filler` → `quantity_calc` → формулы шаблона | Excel |
| 3 | модули | `fill_template_for_room` (в `quantity_calc`) | старый Excel |
| 4 | расчёт | `calculation_excel.py` / `excel_writer.py` | мёртвый код |

Плюс **две схемы модуля** (`quantity` = корпус vs `quantity` = дверь/ящик), **три копии коэффициентов** (`config.py`, `models/settings.py`, `calc_engine.py`) и **три набора цен** (БД, ячейки шаблона, legacy-функции). Отсюда все расхождения: чат не видит кромку, Excel дублирует кромку МДФ, КП не сходится с итогом.

### 4.2. Целевая схема: одно ядро, три представления

```
                    ┌──────────────────────────────────────────┐
   Проект/модули →  │  QuoteService.build_quote(snapshot)      │
   материалы/цены   │  1. QuantityEngine  → BOMLine[]          │
   фурнитура/стекло │  2. PriceResolver   → CostLine[]         │
   коэффициенты     │  3. PricingPolicy   → Quote              │
   версия прайса    │  4. Validator       → инварианты         │
                    └───────────────┬──────────────────────────┘
                                    │  один объект Quote
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
        Telegram-смета          Excel-файл            КП (PDF)
```

**Ключевые объекты (новый доменный слой `app/domain/`):**

- `InputSnapshot` — замороженный вход: модули, ссылки на материалы/фурнитуру, `price_version_id`, `coefficients_version`, `engine_version`, `zone_type`, флаги (`has_spec`, `auto_*`), скидка/наценка.
- `BOMLine` — строка спецификации: `kind` (ldsp/edge/facade/hdf/hardware/glass/lighting/countertop/fastener/service), `sku`, `name`, `quantity`, `unit`, `source_rule` (кто и по какому правилу посчитал), `confidence`.
- `CostLine` — `BOMLine` + `unit_price`, `amount`, `price_source` (прайс/шаблон/ручной ввод), `price_version`.
- `Quote` — `lines[]`, `cost_price`, `pricing` (изготовление, монтаж, проектировка, прочие, прибыль, зарплаты, налоги), `discount`, `total_cash`, `total_noncash`, `warnings[]`, `version`.
- `QuoteValidator` — проверяет инварианты (см. 4.4) и **блокирует** выпуск КП при нарушении.

**Почему это минимальное достаточное вмешательство:** распознавание, `quantity_calc` и шаблон Excel остаются; меняется только способ передачи данных между ними. Не нужны микросервисы, новая СУБД или перепись бота на первом этапе.

### 4.3. Единый источник прайса и коэффициентов

**Прайс.** `PriceItem` получает обязательные атрибуты:

| Поле | Назначение |
|---|---|
| `unit` | `шт` / `м` / `м²` / `лист` / `комплект` — нормализованный enum, не угадывается по имени |
| `thickness_mm` | толщина кромки/плиты отдельным числом (закрывает P0-07) |
| `pack_size` | листов/метров в упаковке, если цена за упаковку |
| `is_active`, `valid_from`, `valid_to` | версионность и деактивация |
| `source_row` | ссылка на строку исходного XLSX для аудита |

**Версия прайса.** Новые таблицы `price_versions` (id, created_at, author, file_hash, comment) и `price_items.version_id`. Импорт создаёт **новую версию**, а не перезаписывает старую; расчёт ссылается на версию. Старое КП не пересчитывается по новому прайсу — это требование аудита и владельца.

**Коэффициенты.** Один объект `PricingPolicy`, загружаемый из `CalcSettings` (профиль по умолчанию) с переопределением из `.env` только для разработки. `calc_engine` больше не содержит чисел. Изменение коэффициента создаёт новую версию политики; расчёт хранит `coefficients_version`.

**Деньги.** Внутри ядра — `Decimal` с квантованием `0.01` и явным правилом округления (`ROUND_HALF_UP` для денег, `ROUND_CEILING` для листов/метража). В БД: SQLite — **целые копейки в `INTEGER`** (`amount_kopecks`, `unit_price_kopecks`) через `TypeDecorator`; PostgreSQL — `Numeric(12,2)`. `Numeric` в SQLite не является фиксированной точкой, поэтому хранить деньги там как `Numeric` нельзя. `float` остаётся только на границе с Excel/JSON и сразу приводится.

### 4.4. Инварианты, которые проверяет `QuoteValidator`

1. `sum(line.amount) == quote.cost_price` (допуск 0,01 ₽). Порядок: сначала округляются количества (листы/метры), затем `amount = qty × price` с `HALF_UP`, `cost_price` — сумма `amount`; инвариант выполняется по построению, а не подгонкой итога.
2. `quote.cost_price == Σ компонентов` (материалы + кромка + фасады + фурнитура + стекло + свет + столешница + крепёж + подрядчики).
3. Нет отрицательных `quantity`, `unit_price`, `amount`.
4. `0 ≤ discount ≤ total_base_cash`; `0 ≤ bonus_rate < 1`; `markup ≥ 0`.
5. `total_cash ≥ cost_price` — иначе предупреждение и запрет КП без ручного подтверждения.
6. У каждой строки есть `source_rule` и `price_version`; «нулевая заглушка» запрещена — либо цена, либо явная строка «не включено» с причиной.
7. `quote.engine_version` и `snapshot.hash` сохранены — расчёт воспроизводим.

### 4.5. Совместимость данных

- JSON-поля `modules`, `selected_materials`, `selected_hardware`, `glass_items` **не удаляются**; рядом добавляется `snapshot` (JSON) и `quote` (JSON) — старые расчёты читаются как есть.
- Новые колонки добавляются только через Alembic с backup; миграция обратима.
- Старые расчёты не пересчитываются автоматически. Для них доступна команда «пересчитать по текущему прайсу» с созданием **новой версии** расчёта, а не изменением старой.
- `Project.calculation` заменяется на `Project.latest_calculation` с `order_by(created_at.desc())`; свойство-обёртка сохраняется для совместимости.

### 4.6. Что сознательно не делается в первые 3 месяца

- Переписывание распознавания и промптов «с нуля» — они не являются причиной финансовых ошибок.
- Переход на PostgreSQL до стабилизации ядра — SQLite достаточен для 1–3 операторов; PostgreSQL появится на этапе 5 вместе с очередью и ролями.
- Веб-интерфейс оператора — только после того, как чат-сценарий и Excel дадут одинаковый итог. Иначе веб просто размножит те же ошибки.
- Микросервисы, Kafka, отдельный price-service — избыточны для текущего объёма.

  5. Переимпортировать прайс в новую версию; старые расчёты не пересчитывать, но пометить «цена требует проверки».

Если толщина не определена — `requires_manual_price`, не угадывать.
- **Файлы:** `app/services/calc_engine.py`, `app/services/price_manager.py`, `app/models/price.py`, `app/bot/handlers/materials.py`, миграция.
- **Зависимости:** P0-01, P1-15b (миграция колонки).
- **Тестирование:** unit: «Кромка 0.8*22» → 0.8; «Кромка 2*19» → 2.0; «Кромка ПВХ 0.4» → 0.4; «Кромка HPL 2 мм» → 2.0; отсутствие толщины → `requires_manual_price`.
- **Критерий приёмки:** ни один тест не зависит от подстроки «2»; словарь цен кромки содержит правильные толщины; итог кромки на эталонном модуле = 549 ₽ (374 ₽ 0,8 мм + 175 ₽ 0,4 мм).
- **Приоритет:** P0 · **Сложность:** S · **Оценка:** 1 день · **Параллельно:** с P0-06.
- **Риски:** в старом прайсе толщина есть только в названии — нужен одноразовый маппинг и ручная проверка всех позиций кромки.

#### P0-06. Excel: одна позиция — одна строка (кромка МДФ)

- **Проблема:** `edge_mdf_1mm_m` пишется в 5 строк разных поставщиков (6 записей маппинга, находятся 5 строк); 6 м → 2 256 ₽ вместо 288 ₽.
- **Причина:** шесть записей `row_mapping` используют одно поле; цикл заполнения пишет в каждую найденную строку; `quantity_calc` возвращает **общий** метраж без разбивки по поставщику, поэтому распределить его по строкам нечем.
- **Решение:** (1) разделить поле на `edge_mdf_1mm_emdiway`, `..._evo`, `..._agt`, `..._eterno`, `..._smart`, `..._kromka`; (2) в `template_filler` выбирать **одну** строку по выбранному типу фасада, остальные оставлять пустыми; (3) если в проекте несколько типов фасадов — не писать весь объём в каждую строку: выбрать основной тип по площади и показать предупреждение «требуется распределение по поставщикам»; полноценное распределение — после BOM (S5-01), а не выдумывать его в Excel; (4) добавить инвариант «одно поле — не более одной строки» в валидатор; (5) тест на шаблоне: 6 м EMDIWAY (один поставщик) → ровно одна строка, 288 ₽.
- **Файлы:** `templates/row_mapping.json`, `app/services/template_filler.py`, `app/services/quantity_calc.py` (поле), тест.
- **Зависимости:** P0-02 (кромка МДФ должна быть в `CostLine`).
- **Тестирование:** открыть сгенерированный Excel, найти все строки с `1*22`; заполнена ровно одна; сумма = `edge_mdf_1mm_m × цена`; тест на 37 м → 1 776 ₽; тест на два типа фасадов → одна строка + предупреждение.
- **Критерий приёмки:** на тестовом шаблоне нет дублей; сумма кромки МДФ в Excel равна переданному `CostLine`; сверка с чатом — после P1-01.
- **Приоритет:** P0 · **Сложность:** S · **Оценка:** 1 день · **Параллельно:** с P0-07.
- **Риски:** шаблон может измениться у собственника — маппинг должен быть в JSON, а не в коде; после изменения шаблона тест падает и требует обновления.

#### P0-08. Валидация скидок, наценок, ставок и стоимостей

- **Проблема:** скидка 1 000 000 ₽ при цене 1 500 → −983 216 ₽; 150% → отрицательная цена; бонус 1,0 → `ZeroDivisionError`; отрицательная стоимость материала проходит; скидка и наценка одновременно — молча применяется только скидка.
- **Причина:** в `calculate_cost` нет проверок входов; UI принимает любое положительное число; `discount`/`markup` обрабатываются как `elif`.
- **Решение:** (1) Pydantic-модель `DiscountInput` с ограничениями: `percent ∈ [0,100]`, `fixed ∈ [0, base]`, `bonus_rate ∈ [0, 0.99]`, стоимости ≥ 0; (2) в `calculate_cost` — явные `ValueError` с понятным текстом; (3) запрет одновременных скидки и наценки (или явное правило приоритета); (4) нижняя граница `final_cash ≥ cost_price` с предупреждением и запретом КП без подтверждения; (5) в боте — валидация на вводе и подтверждение суммы; (6) тесты на все границы.
- **Файлы:** `app/services/cost_calc.py`, `app/bot/handlers/discounts.py`, `app/models/calculation.py`, новый `app/domain/validation.py`.
- **Зависимости:** нет (можно параллельно с P0-02).
- **Тестирование:** таблица границ: 0%, 100%, 100,01%, −1%, 1 000 000 ₽, скидка = базе, скидка > базы, бонус 0, 0.99, 1.0, 1.5, отрицательная стоимость. Ожидание: валидные считаются, невалидные — понятная ошибка, не отрицательный итог.
- **Критерий приёмки:** ни один вход не даёт отрицательный `final_cash`; `ZeroDivisionError` невозможен; UI показывает ошибку до расчёта; тесты покрывают все границы.
- **Приоритет:** P0 · **Сложность:** S · **Оценка:** 1 день · **Параллельно:** да.
- **Риски:** собственник использует скидку > 100% как «доплату» — уточнить (вопрос Q3); если да, нужен отдельный тип «корректировка».

#### P1-23. Стоимость листов по каждому материалу, без средней цены

- **Проблема:** одна средняя цена применяется ко всем листам; при двух ЛДСП разных брендов стоимость неверна.
- **Причина:** `_get_average_sheet_price` усредняет выбранные материалы; `selected_materials` хранит только один `ldsp`.
- **Решение:** (1) `selected_materials['ldsp']` → список позиций с количеством листов или долей; (2) `quantity_calc` возвращает листы по бренду/декору; (3) `material_cost = Σ(sheets_i × price_i)`; (4) если распределение неизвестно — использовать цену основного материала и предупреждение, не среднее.
- **Файлы:** `app/services/calc_engine.py`, `app/services/quantity_calc.py`, `app/bot/handlers/materials.py`, `app/models/calculation.py`.
- **Зависимости:** P0-01.
- **Тестирование:** два ЛДСП 6 000 и 8 000, 2 и 1 лист → 20 000, не 21 000 и не 18 000; тест на один материал — без изменений.
- **Критерий приёмки:** стоимость материалов равна сумме по каждому материалу; средняя цена не используется.
- **Приоритет:** P1 · **Сложность:** S · **Оценка:** 1–2 дня · **Параллельно:** с P0-06.
- **Риски:** UI сейчас выбирает один ЛДСП — потребуется расширить выбор; на первом этапе можно считать по одному, но запретить «среднее».

#### P1-03. Двухдверный корпус — один модуль, а не N модулей

- **Проблема:** две двери 300 мм превращаются в два модуля 300×560×820; ЛДСП +37%, кромка +18%.
- **Причина:** `_facades_to_modules` группирует по ширине двери и ставит `quantity=len(group)`, `width=avg_width` (ширина двери), `facades.count=1`.
- **Решение:** (1) группировать по x-смежности и сумме ширин в корпус; (2) `width = Σ ширин дверей + технологические зазоры`, `quantity=1`, `facades.count = N`; (3) если модель даёт `module_id/carcass_id` — использовать его; (4) валидация: сумма ширин фасадов ≤ ширины корпуса; (5) тест на 2, 3, 4 двери.
- **Файлы:** `app/services/image_analyzer.py`, `app/services/scale_calc.py`, `prompts/unified.txt` (при необходимости), тест.
- **Зависимости:** нет (но результат влияет на P0-02).
- **Тестирование:** 2 двери 300 → 1 модуль 600, ЛДСП 2,509 м², кромка 11 м; 3 двери 400 → 1 модуль 1200; **регресс на 12 страницах эталонного альбома**: ожидаемые ширины/число фасадов/ящиков, допуск ±1 модуль и ±30 мм; сравнение до/после.
- **Критерий приёмки:** на эталонном двухдверном модуле площадь и кромка совпадают с ручным расчётом; нет модулей с `facades.count=1` и `quantity=N` для рядом стоящих дверей.
- **Приоритет:** P1 · **Сложность:** M · **Оценка:** 3–4 дня · **Параллельно:** с P1-04.
- **Риски:** изменение геометрии влияет на распознавание всех листов — прогнать эталонный альбом и сравнить 12 страниц; возможен регресс на угловых кухнях. При правке промпта синхронизировать `prompts/unified.txt` и вшитую копию в `image_analyzer.py` (правило проекта).

#### P1-04. Количество ящиков на фасад, а не всегда 1

- **Проблема:** блок из 3 ящиков даёт 1 ящик.
- **Причина:** `drawer_indices` — номера фасадов, код ставит `drawers={"count":1}`.
- **Решение:** (1) расширить промпт: `drawer_counts: {facade_index: N}` или `drawer_indices` с количеством; (2) парсить горизонтальные линии внутри фасада как число ящиков; (3) валидация: 1 ≤ count ≤ 4; (4) при отсутствии данных — 1 и предупреждение «проверить количество ящиков».
- **Файлы:** `prompts/unified.txt`, `app/services/image_analyzer.py`, `app/services/quantity_calc.py`, тест.
- **Зависимости:** P1-03 (та же геометрия).
- **Тестирование:** лист с блоком 3 ящиков → `drawers.count=3`, `drawers_count=3`, стоимость = 3 × цена; лист с 1 ящиком — без изменений.
- **Критерий приёмки:** на эталонном листе число ящиков совпадает с ручным подсчётом технолога; в смете видно количество.
- **Приоритет:** P1 · **Сложность:** S/M · **Оценка:** 1–2 дня · **Параллельно:** с P1-03.
- **Риски:** модель может путать ящики с полками — нужен операторский просмотр; не менять основную vision-модель на слабую. Промпт синхронизировать в `prompts/unified.txt` и `image_analyzer.py`.

#### P1-17. Фасады: одно правило учёта, без двойного ЛДСП+ПВХ

- **Проблема:** при неизвестном типе фасада площадь добавляется в ЛДСП ×1,15 и одновременно маппится в «ФАСАДЫ ПВХ 16 мм».
- **Причина:** `facade_type == "unknown"` трактуется как «ЛДСП-фасад» в `quantity_calc` и как «ПВХ» в `template_filler`.
- **Решение:** (1) ввести явный `facade_type` с обязательным выбором оператора (МДФ-плёнка, МДФ-лак, ЛДСП, стекло, алюминий); (2) при `unknown` — **не** добавлять в ЛДСП и **не** маппить в ПВХ, а показывать «тип фасада не выбран» и блокировать КП; (3) если ЛДСП-фасад — учитывать один раз, без ПВХ; (4) тест на каждый тип.
- **Файлы:** `app/services/quantity_calc.py`, `app/services/template_filler.py`, `app/bot/handlers/materials.py`, `templates/row_mapping.json`.
- **Зависимости:** P0-02, P1-23.
- **Тестирование:** EGGER + явный ПВХ → 3 листа, 0,5 м² ПВХ; EGGER + unknown → ошибка/предупреждение, не 4 листа + ПВХ; EGGER + ЛДСП-фасад → 4 листа, без ПВХ.
- **Критерий приёмки:** площадь фасадов учитывается ровно один раз; тест «один фасад — один тип».
- **Приоритет:** P1 · **Сложность:** M · **Оценка:** 2 дня · **Параллельно:** с P1-18.
- **Риски:** старые расчёты без типа фасада станут «невалидными» — пометить, не ломать; миграция не требуется.

#### P1-18. Excel: строки и итог для крепежа и столешницы

- **Проблема:** столешница 5 м, конфирмат 260, опоры 28, подвесы 14 не входят в себестоимость; уходят в «⚠ Проблемы».

#### P1-19. Стекло: ввод размеров и тарификация

#### P1-02. Автопозиции — opt-in, а не по умолчанию

- **Проблема:** для кухни автоматически добавляются 2+1 ящика, GOLA, LED, сушка, лоток, бутылочница — до 36 366 ₽ на помещение (блок добавляется один раз на кухню, не на каждый модуль; аудит формулирует «на модуль», код — на комнату).

- **Файлы:** `app/services/quantity_calc.py`, `app/services/calc_engine.py`, `app/bot/handlers/calculation.py`, `app/services/template_filler.py`.
- **Зависимости:** P0-02, P1-20.
- **Тестирование:** кухня без подтверждения → 0 автопозиций; с подтверждением → ровно выбранные; `has_spec=True` → 0.
- **Критерий приёмки:** ни одна платная позиция не появляется без действия оператора; смета объясняет каждую строку.
- **Приоритет:** P1 · **Сложность:** M · **Оценка:** 2–3 дня · **Параллельно:** с P1-20.
- **Риски:** оператор привык, что система «сама добавляет» — обучить; иначе рост ручной работы.

#### P1-20. `zone_type` сохраняется и передаётся в расчёт

- **Критерий приёмки:** зона влияет на состав сметы предсказуемо; в смете видно зону.
- **Приоритет:** P1 · **Сложность:** S · **Оценка:** 1 день · **Параллельно:** с P1-02.

### 5.3. Этап 2. Единая расчётная система (месяц 2, недели 5–8)

> Цель этапа — сделать невозможным расхождение чата, Excel и КП. После этапа 2 любое расхождение — дефект, а не «особенность формата».

#### P1-01. Один набор коэффициентов и один прайс для чата, Excel и КП

- **Проблема:** доставка 6 500 vs 10 000; проектировка 10% изготовления vs 8% себестоимости; Excel не умеет скидку/наценку/бонус; цены чата из БД, Excel — из ячеек шаблона.
- **Причина:** шаблон Excel содержит собственную финансовую модель; `template_filler` не получает `Quote`; `cost_calc` и формулы шаблона развивались отдельно.
- **Решение:**
  1. `QuoteService.build_quote(snapshot)` — единственная точка расчёта.
  2. Excel получает **готовые суммы** (`Quote.lines`, `Quote.totals`) в лист «Итоги» **выходной копии**. Лист «Рассчет» сохраняет формулы как контроль, но клиентская копия не зависит от их пересчёта; расхождение формулы с `Quote` — ошибка валидатора, а не выбор одного из значений.
  3. Скидка/наценка/бонус считаются до Excel и передаются строками.
  4. Коэффициенты — из `PricingPolicy` (одна версия), не из ячеек.
  5. Тест: один snapshot → три выхода; `quote_hash` одинаков.
- **Файлы:** новый `app/domain/quote_service.py`, `app/services/template_filler.py`, `app/services/cost_calc.py`, `app/services/kp_generator.py`, `templates/Таблица для расчетов пустая.xlsx`.
- **Зависимости:** P0-02, P0-06, P1-09, P1-18. Цикла нет: P1-09 и P1-18 выполняются **до** P1-01 и от него не зависят.
- **Тестирование:** golden-тест на 3 сценариях: чат = Excel = КП по каждой строке и итогу; тест на скидку 5% → одинаковая сумма во всех трёх; тест на доставку 6 500/10 000 — одна цифра.
- **Критерий приёмки:** расхождение итогов ≤ 0,01 ₽; в Excel нет «своих» коэффициентов; КП печатает те же строки.
- **Приоритет:** P1 · **Сложность:** L · **Оценка:** 10–14 дней · **Параллельно:** нет (ядро).
- **Риски:** большой рефакторинг; риск сломать Excel-шаблон. Смягчение: сначала «теневой режим» — считать оба пути и сравнивать, переключать вывод после 10 совпадений.

- **Файлы:** `app/config.py`, `app/models/settings.py`, `app/services/calc_engine.py`, `app/services/cost_calc.py`, `app/bot/handlers/calculation.py`, `discounts.py`.

#### P1-10. Полный `CostBreakdown` сохраняется и печатается в КП

#### P1-24. Decimal/копейки и единая политика округления

- **Проблема:** деньги во Float; банковское округление; накопление ошибок; `Numeric` в SQLite не даёт фиксированной точки.
- **Причина:** модели `Float`, `round()` в расчётах; SQLite хранит NUMERIC с плавающей точкой.
- **Решение:** (1) `Decimal` в домене; (2) **SQLite — целые копейки** в `INTEGER` (`amount_kopecks`, `unit_price_kopecks`) + `TypeDecorator`, `Numeric(12,2)` — только для PostgreSQL; (3) порядок округления: сначала количества (листы/метры — `ROUND_CEILING`), затем `amount = qty × price` (`ROUND_HALF_UP`), `cost_price = сумма amount` — инвариант выполняется по построению; (4) миграция батчами по 500 расчётов с rollback и сверкой старых итогов; (5) тест на 0,1+0,2 и на 10 000 строк.
- **Файлы:** `app/models/calculation.py`, `app/services/cost_calc.py`, `app/services/calc_engine.py`, `app/domain/money.py`, миграция.
- **Зависимости:** P1-01, P1-15b (Alembic); миграция — после P1-15c (бэкап/WAL).
- **Тестирование:** property-тест «сумма строк = итог» на 10 000 случайных наборов; сравнение с эталоном в Excel; отсутствие `float` в домене (grep/линтер); rollback батча.
- **Критерий приёмки:** в SQLite суммы — целые копейки; расчёт детерминирован; повторный пересчёт даёт ту же сумму до копейки; миграция обратима.
- **Приоритет:** P1 · **Сложность:** L · **Оценка:** 10–15 дней · **Параллельно:** после P1-01; можно параллельно с P1-10.
- **Риски:** массовая замена типов; обязательна миграция с бэкапом и сверкой старых итогов; `Numeric` в SQLite нельзя считать фиксированной точкой.

#### P1-26. Golden-тесты «модули → итоговая цена»

- **Проблема:** 343 теста зелёные при подтверждённых ошибках цены; нет E2E.

- **Файлы:** `tests/golden/`, `tests/test_quote_golden.py`, `tests/test_excel_parity.py`, `.github/workflows/ci.yml`.

### 6.3. Действующая формула (зафиксировать как baseline)

```
cost_price = Σ компонентов (1…10)
manufacturing = round(cost_price × 0.80)
installation  = round(cost_price × 0.55)
measurement   = 2500
delivery_int  = 6500
design        = round(manufacturing × 0.10)
overhead      = round(cost_price × 0.05)
subtotal      = cost_price + manufacturing + installation + measurement + delivery_int + design + overhead
profit        = round(subtotal × 0.30)
total_with_profit = subtotal + profit
tech_director = round(total_with_profit × 0.015)
total_base_cash = total_with_profit + tech_director + manager + designer
discount / markup → price_after_discount
bonus: final_cash = price_after_discount / (1 − bonus_rate)
noncash = final_cash × 1.13
```

**Наблюдение:** «прибыль 30%» — это наценка на промежуточный итог, а не маржа. Доля прибыли в цене наличными ≈ 23,1% (0,3 / 1,3). Если собственник имел в виду маржу 30%, коэффициент должен быть 0,3 / 0,7 ≈ 0,4286. Это вопрос Q1, а не задача разработчика.

**Проверка арифметики:** при `cost_price = 100 000` чат даёт 339 112 ₽ (изготовление 80 000, монтаж 55 000, замер 2 500, доставка 6 500, проектировка 8 000, прочие 5 000, прибыль 77 100, техдиректор 5 012). Excel при тех же компонентах, но доставке 10 000 и проектировке 8% себестоимости — 343 730 ₽ (+4 618 ₽). Расхождение арифметически объяснимо и устраняется только единой политикой.

### 6.4. Целевая формула

```
Quote = PricingPolicy.apply(Σ CostLine)
PricingPolicy:
  manufacturing_rate, installation_rate, design_rate, overhead_rate,
  profit_rate, tech_director_rate, manager_rate, designer_rate,
  measurement_fee, delivery_internal_fee, delivery_client_fee,
  noncash_markup, tax_rate?, rounding_policy
```
Все параметры — версионированные, с автором и датой. Скидка/наценка/бонус — отдельные объекты с валидацией. `Quote.totals` содержит `cost_price`, `services`, `profit`, `taxes`, `total_cash`, `total_noncash`. **Ни одна формула не живёт в Excel или в боте.**

## 7. План тестирования и критерии приёмки

### 7.1. Принципы

1. **Тест проверяет деньги, а не функции.** Минимальная единица приёмки — `Quote` на эталонном входе, а не «функция вернула число».
2. **Ручной эталон первичен.** Эталон считает технолог/QA в Excel по подтверждённым нормативам, а не разработчик по коду. Иначе тест зафиксирует ту же ошибку.
3. **Один вход — три выхода.** Чат, Excel и КП сравниваются на одном `snapshot`; расхождение > 0,01 ₽ — дефект.
4. **Тесты не содержат ПДн.** Только синтетические или обезличенные заказы.
5. **Каждый исправленный дефект получает регрессионный тест** с ссылкой на ID (например, `test_p0_02_edge_included`).

**Чувствительность срока:** при одном backend вместо двух G2 сдвигается на 4–6 недель, G4 — на 2–3 месяца; при QA 0,5 вместо 1,0 golden-набор и приёмка замедляются вдвое. Три месяца достигаются только при полной загрузке двух разработчиков, QA 1,0 и доступе технолога к эталонам в первую неделю. Если эталонные заказы не получены к концу недели 1, G2 сдвигается на 2–3 недели, а пилот — на месяц 3.

### 8.4. Критический путь

`P1-15 (бэкап) → P0-01 (прайс) → P0-02 (компоненты) → P0-07/P0-06 → P1-09/P1-18 → P1-01 (единое ядро) → P1-24 (копейки) → P1-10 (КП) → P1-26 (13/13) → G2 → пилот → G3`.

## 10. Решения, необходимые от собственника

До ответов система работает в режиме «черновик» и **не выпускает КП без подтверждения**. Для каждого вопроса указан безопасный дефолт — он не заменяет решение, а позволяет не останавливать разработку.

| **Q2** | Клиентская доставка 10 000 ₽ входит в базу для прибыли/безнала или начисляется отдельно? | Сейчас в чате не входит, в Excel входит | Входит в итог отдельной строкой, не в базу прибыли | высокая |
| **Q3** | Допустима ли скидка больше базы/100%? | Сейчас даёт отрицательную цену | Запрет: 0…100%, фикс ≤ базы | высокая |

## 13. Результаты независимой проверки плана

### 13.1. Кто и как проверял

План проверен отдельным Senior Software Architect, который **не участвовал** в его составлении и не видел переписки. На вход поданы: план, полный текст итогового аудита, `AGENTS.md` и доступ к репозиторию. Проверялись:

- полнота: все ли 59 ID из аудита присутствуют и не дублируются;
- порядок и зависимости: нет ли циклов, не нарушен ли критический путь;
- противоречия между этапами, категориями A/B/C, гейтами G0–G4 и сроками;
- новые риски от предлагаемых исправлений;
- реалистичность оценок на заявленную команду;
- достаточность тестов и критериев приёмки;
- выборочно — 10 ссылок на файлы и строки;
- отсутствие выдуманных нормативов и цен.

### 13.2. Вердикт первой проверки

**«Доработать, не готов».** Главные причины:

1. Циклы зависимостей и невыполнимые гейты G1–G4: `P1-01` зависел от `P1-09`/`P1-18`, которые зависели от `P1-01`; G1 требовал parity за 2 недели, хотя `P1-01` стоял в этапе 2; G2 за 1 месяц не сходился с 24–33 днями только на ядро.
2. Эталон №1 требовал объяснения: периметр 20,02 м включает заднюю стенку (спорная эвристика P2-07); без неё метраж ≈16,33 м. Это не ошибка арифметики, а **незафиксированное допущение**, которое тест не должен молча наследовать.
3. Неполные исправления: `P0-01` описывал «сканирует имя», хотя fallback перебирает всю строку; `P0-06` не распределял количество между поставщиками; `Numeric` в SQLite не даёт фиксированной точки.
4. Сроки и ресурсы: QA 0,5 и технолог 0,2 недостаточны для 13 эталонов; G2/G3/G4 были заявлены слишком рано.

### 13.2a. Вторая проверка

После внесения правок тот же независимый архитектор проверил **только исправления**. Вердикт: **«доработать»**, закрыты 5 из 8 критических пунктов; остались блокеры:

4. `P1-18` заявляла «не зависит от P1-01», но критерий «итог Excel = итог чата» до P1-01 невыполним.

- [ ] Runbook, обученный оператор, подписанная финансовая политика, политика ПДн.
- [ ] Регламент поддержки: кто отвечает, время реакции, как сообщать о проблеме.
- [ ] План следующего этапа: PostgreSQL, RBAC, API, CRM — только после G3.

**Чего через три месяца ещё не будет:** G4 (10 заказов, ≥80% без правок), полный каталог, раскрой, PostgreSQL. Это месяцы 4–6.

## Приложение C. Как соблюдены правила разработки

| Правило | Как выполнено |
|---|---|
| Не переписывать с нуля | Сохраняются распознавание, `quantity_calc`, шаблон; меняется слой расчёта и передачи данных |
| Не менять рабочее без причины | Каждая задача имеет дефект, доказательство и тест |
| Не удалять функционал без согласования | Удаление `edge_calc`, мёртвого кода — после подтверждения и с тестом |
| Не менять формулы без собственника | Q1–Q20; baseline фиксируется, изменения — версией политики |
| Не придумывать нормативы | Все эвристики помечены «допущение»; нормативы — от технолога |
| Не смешивать независимые проблемы | Отдельные карточки и коммиты; P0-02 разбит на компоненты |
| Не считать «код изменён» завершением | Критерий — тест + приёмка технолога |
| Каждое исправление с тестом | Регрессионный тест с ID дефекта |
| Совместимость данных | JSON сохраняется, новые поля через Alembic, старые расчёты `legacy` |
| Бэкап перед изменением БД | P1-15, тест восстановления |
| Малые коммиты | Один дефект — один коммит/PR |
| Не публиковать без разрешения | Force-push и публикация — только по Q12 |

## Приложение D. Источники и ограничения

**Источники:** итоговый отчёт аудита (15.11.2026), проверка на HEAD `c6d2fd5`; `pytest` 343 passed; чтение кода; запросы к локальной БД; синтетические расчёты; gitleaks/git-история; шаблон Excel.
